How an oncoprint is drawn on the analysis page

Two requests: the analysis run says what to draw, then the card fetches the oncoprint itself from its own endpoint.

Browser

1
The analysis request, as for every view
use-analysis.ts → api.ts → POST /api/analysis?oncoprint=spec
?oncoprint=spec means "the page draws the oncoprint itself; just tell it what to fetch".
↓document JSON

Server: request 1, the analysis

2
runAnalysis → lib/views/oncoprint/run.ts in spec mode
cohorts are compiled and counted as usual (step 3 of the analysis call stack)
the oncoprint runner then runs no queries; it returns a spec:
the studies it may use · genes · clinical + heatmap tracks · sort · display · any z-score reference across studies
the cohort definitions (not their SQL)
Compiled SQL never leaves the server, so the page receives definitions and the next request compiles them again.
↓analysis result: other views' numbers, plus the oncoprint's spec

Browser

3
The card fetches its own figure
app/lab/kinds/oncoprint.tsx → app/_oncoprint/OncoprintCard.tsx → OncoprintFigure.tsx
api.oncoprint(spec) → POST /api/oncoprint?format=bin
Fetched again only when the spec changes. The other cards are already drawn by now.
↓spec JSON

Server: request 2, the oncoprint

4
app/api/oncoprint/route.ts
parseBody → withRequestCustomData → cachedContract (lib/next-cache.ts)
→ buildContract (lib/oncoprint.ts): compiles the cohorts again, queries ClickHouse (a peer instance answers its own share)
→ assembleContract (lib/oncoprint-assemble.ts, pure): one column per patient, cells as bitmasks, "not profiled" as its own state
→ packContract (lib/oncoprint-binary.ts): the OPB1 binary, gzipped
SQL: the cohorts are compiled a second time here, then the oncoprint's own row queries are built in lib/oncoprint.ts.
↓binary contract: typed arrays, about half of it patient ids

Browser

5
Decode and draw on a canvas
unpackContract → app/_oncoprint/canvas.ts draw(), with its colours and glyphs from lib/oncoprint-style.ts
interactions go back to the same endpoint family:
hover a column → /api/oncoprint/detail (the details behind that column's bitmask)
drag-select sample columns → /api/oncoprint/patients-of → a patient cohort
download → /api/oncoprint?format=svg or tsv, with the sort shown on screen
JSX: OncoprintCard / OncoprintFigure. The figure is canvas pixels, not an SVG string.

Why the oncoprint has its own endpoint

• Size: other views return a few hundred numbers. An oncoprint has one column per patient, often tens of thousands, so it goes as packed binary, not JSON.
• Nothing waits for it: the analysis response holds no oncoprint queries, so the other cards draw first.
• Its own cache entry: the contract is cached by its spec, so re-running the analysis for an unrelated change can reuse it.
• Other callers: /local (pasted Oncoprinter tables, no database), /notebook (the figure as a Jupyter notebook), the /oncoprint-lab pages.
• Other routes: MCP asks ?oncoprint=svg. The runner then builds the contract in the same request, reusing the cohort SQL it already compiled (PIDS_SQL), and returns server SVG (lib/oncoprint-svg.ts). The CLI and python/cohortlab draw the same contract.
• Cost: on the page, each cohort is compiled twice: once in step 2 to count it, and again in step 4 from the definitions in the spec.

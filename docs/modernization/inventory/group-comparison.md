# Inventory: Group comparison (GC-)

1. **Area:** Group comparison page (`/comparison/:tab?`) and every tab on it (Overlap, Survival, Clinical, Genomic Alterations, Mutations, Pathways, mRNA, Protein, DNA Methylation, generic-assay tabs), plus the group-creation and session pieces it depends on.
2. **Source paths** (all under `cbioportal-frontend/src/`): `pages/groupComparison/` (page, store, tabs, group selector, group manager, venn/upset), `shared/lib/comparison/` (`ComparisonStore.ts`, `ComparisonStoreUtils.ts`, `ComparisonTabUtils.tsx`, `AlterationEnrichmentTypeSelector.tsx`), `pages/resultsView/enrichments/` (shared enrichment tables and plots), `pages/resultsView/survival/` (KM chart, log-rank, hazard ratio), `shared/api/session-service/`, `shared/lib/calculation/`. Backend checked for test names only: `/home/user/cbioportal/src/main/java/org/cbioportal/legacy/{service/util,web/util}`.
3. **Size:** `pages/groupComparison/` = 61 files / 17,899 lines (7 unit-spec files, about 4,750 lines of them specs); `shared/lib/comparison/` = 5,058 lines; `pages/resultsView/enrichments/` = about 9,500 lines (shared with the results-view comparison tab).
4. **Features listed:** 95 (rows GC-001 to GC-152).
5. **With E2E coverage:** 66 of 95 have at least one Playwright spec (a screenshot-only spec counts); the rest are `none`.

Conventions: paths are relative to `cbioportal-frontend/src/`. "Session service" = the separate session-service REST API under `getSessionUrl()` (`api/session`, see `shared/api/urls.ts`); it is not in `packages/cbioportal-ts-api-client`. Statistical tests that run on the Java backend were read from `/home/user/cbioportal` (path given in Notes) and are marked "backend". E2E file names are in `end-to-end-test-playwright/tests/` (`local/` = local-DB lane). Specs that load a hard-coded session id (e.g. `sessionId=5ce411c7e4b0ab4137874076`) use data on the public server, so their contents can drift.

## Statistical tests reference (must be reproduced exactly)

q = Benjamini-Hochberg is `calculateQValues` in `shared/lib/calculation/BenjaminiHochbergFDRCalculator.ts`: input p-values sorted ascending; walking from the largest, q_i = min(q_{i+1}, p_i * n / rank_i), with q for the largest p equal to p. The implementation tests `if (cachedElement)`, so once a computed q equals exactly 0 the chain restarts from the next p; it also reverses its argument in place. "Significant" everywhere = q < 0.05 (strict).

## Open questions

1. **Clinical numeric test for 2 groups.** The backend labels it "Wilcoxon Test" but computes `KruskalWallis.getPvalue`. Is the Kruskal-Wallis chi-square p (with its tie correction, `?`) acceptable as the reference, or must a transform reproduce Mann-Whitney U? The UI tooltip names only Chi-squared and Kruskal-Wallis. The Datumbox implementation was not read.
2. **Backend tests are the numbers users see.** The expression tests (Welch t, classic ANOVA), clinical tests and alteration Fisher/chi-square run in the Java backend and were read from the repo checkout `/home/user/cbioportal`. Is that checkout the deployed version, and should reproduction cite it or the live API as ground truth? There is also a second clinical-enrichment implementation under `domain/clinical_data_enrichment/` that was not compared.
3. **Which survival variants must be reproduced?** The portal pools patients across studies with no stratification and no minimum, uses a hazard ratio that is an O/E ratio (not Cox), and treats an unparseable status as censored. cBioLab's `survival` view stratifies by study and refuses under 10 per arm. Is parity wanted, or is cBioLab's stricter method the target with a documented difference?
4. **Include mode semantics.** In Include mode the survival tab compares "Only A, B" partitions, while the clinical and alteration tabs analyse the stored groups. Should cBioLab expose an include/exclude overlap option on its views, or only keep the `overlap` view?
5. **Sample vs patient level.** Portal enrichments run per sample (default) or per patient (alterations tab only); the sample-level frequency denominators are per-gene profiled samples. cBioLab `enrichment` is sample-only and `diffexpr` is patient-averaged. Should the patient-level alteration option be added?
6. **Group identity.** Portal groups are saved sample lists in sessions (immutable, new session on every edit, names unique per session); cBioLab cohorts are definitions. How should a "group created from an overlap region" or a "chart-category group" be represented (definition vs stored id set)? Note cBioLab's `/groups` page is about sharing access, a different meaning of "group".
7. **Mutations tab.** The mirrored lollipop (two groups, % or count axis, per-group badges, per-protein-change Fisher and BH) has no cBioLab counterpart; `mutations` is a one-gene table. Is the lollipop in scope for the rebuild?
8. **Suspected bugs not to copy blindly:** `profiledPatientCounts` is positional over an object keyed by group name; the "Most significant p-value" gene list comparator returns 0 when both p are defined; the BH `if (cachedElement)` restart on q = 0; the significance filter skipped when q = 0; clinical q-values include attributes later hidden (survival, GENIE). Which should a transform preserve for numerical parity and which fix?
9. **Config-driven behaviour.** `survival_min_group_threshold` (3), `survival_show_p_q_values_in_survival_type_table`, `comparison_categorical_na_values`, `skin_show_settings_menu`, `skin_hide_download_controls`, `skin_comparison_view_mutation_table_columns_show_on_init`, and feature flags `LEFT_TRUNCATION_ADJUSTMENT` and `group_comparison_pathways` change what users see. Which defaults does the rebuild adopt?
10. **E2E reality check.** Most group-comparison specs are screenshot tests against sessions on the public server (hard-coded ids), so they confirm rendering, not numbers; only `local/comparison-alterations-tab.spec.ts` asserts counts (`ALK 2 (18.18%)`, row counts 8 and 2, `ACAP3 9 (1.17%)` then `7 (0.91%)`). Should the transform reproduction be validated against those local-DB studies rather than the screenshots?
